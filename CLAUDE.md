# Kagura Memory SDK - Development Guide

## Overview

Python SDK for Kagura Memory Cloud. Seven clients:
- `KaguraClient` — MCP client for memory and context operations
- `ResourceClient` — REST client for resource token management and data ingestion
- `FilesClient` — REST + presigned PUT client for file uploads with sha256 integrity binding (server v0.15.1+)
- `SecretClient` — REST client for the zero-knowledge secret store (age recipient encryption, local decrypt; `[secret]` extra, server v0.39.0+)
- `WorkspaceClient` — REST client for workspace member/invitation management (owner API key only, OAuth rejected; server v0.42.0+); `list_operation_history` takes a web session only (server v0.154.0+)
- `AgentsClient` — REST client for the agent control plane: bootstrap (`POST /api/v1/agents/{agent_id}/bootstrap`) + registry/binding CRUD (owner/admin; server v0.49.0+)
- `MemoryClient` — REST client for tool guardrails: `load_guardrails` (`POST /api/v1/memory/guardrails`) + the `AGENTS.md` digest (`GET /api/v1/memory/guardrails/digest`) for API-key-only hooks and scripts (server v0.74.0+)

Checked against memory-cloud up to **v0.161.0** (#340; v0.47.0). `MIN_SERVER_VERSION` stays **0.17.1** and is advisory; newer surfaces carry their own server floor in `docs/compatibility.md` (one section per SDK release, newest first; a release adds its section there and a row to the README's five-release summary).

## Key SDK Features

- Context management: `create_context`, `update_context` (with `resource_id`, `is_public`)
- Search tuning: `update_search_config` (semantic/bm25 weights, reranking). `recall(use_rerank=...)` is tri-state (server v0.69.0+, #251): `None` (default) omits the arg so the context's `search_config.use_rerank` applies (with `context_ids`, the first context's), `True` requests reranking (context must enable it), `False` is SENT to skip it; CLI `kagura recall --rerank/--no-rerank`
- **Server info + docs realign** (v0.39.0, #257): `get_server_info().features` types every v0.77.0 `/api/v1/system/info` flag (`neural_memory`, `research_tools`, `plan_page`, `byok`, `cost_display`, `managed_connectors`, `managed_llm`, `referrals`, `beta_invites`, `reranking`; the v0.76.0 set) as `bool = False` (`False` = not reported) with `extra="allow"` (newer flags → `features.model_extra`); `ServerInfo.search_defaults` = reranker defaults for new contexts (server v0.69.0+); `ServerInfo.terms_version` (v0.41.0, #282) = the terms-of-service version (server v0.77.0+, memory-cloud#1665), `None` when the deployment records no acceptance or on an older server — acceptance is a web sign-in step, never gates API/MCP calls. Docstrings track the server: `load_pinned` → `memories` (never `results`); forget retention is per deployment (`CLEANUP_DELETED_MEMORIES_RETENTION_DAYS`, v0.66.0+) and `forget(query=...)` is refused while recall is `degraded`; recall `degraded`/`degraded_reason`, `tag_suggestions`, `filters.tags_normalize`, empty per-result keys omitted (v0.73.0+); `merge_contexts` counts rows + `pending_embedding`; public contexts/resources/tokens plan-gated (`plan_required`; since v0.68.0 by the `public_contexts`/`resources` plan feature, XL-only by default — earlier by the plan's shared contexts/token cap); reranker providers are `voyage|cohere|self_hosted` only (`self_hosted` v0.42.0+); `mcp_url` may carry `?profile=`/`?tools=` (v0.73.0+) and `?add_tools=` (v0.129.0+), which shape `tools/list` only: `core` is the default listing since 0.93.0; `?profile=full` lists everything
- Resource ingestion: `setup_resource`, `ingest_event`, `ingest_events`
- Resource stats/schema: `get_resource_impact`, `get_resource_schema`
- **File uploads**: `FilesClient.upload/download_url/delete/list` with R2 sha256 binding (server v0.15.1+); optional `binding_context_id` binds a file to an owning context for ACL + nullable `FileObject.context_id` (server v0.41.0+). Against v0.41.0 the file-id endpoints require `workspace_id` on the query, so `download_url`/`delete` take a **required** `context_id` and the PUT sends the checksum header only when the presign signed it (#226)
- **Zero-knowledge secrets**: `SecretClient` + `kagura secret` — age recipient encryption, local decrypt; private key in OS keychain via `pyrage`/`keyring` (`[secret]` extra, server v0.39.0+). Owner-only hard delete via `SecretClient.delete_secret` / `kagura secret delete` (server v0.41.0+)
- **Member context access** (v0.45.0, server v0.144.0+): `WorkspaceClient.add_member(allowed_context_ids=...)` and `get_member_context_access/set_member_context_access` take an owner key; `None` restores role defaults and `[]` grants no contexts on set. `WorkspaceClient.from_web_session(...).add_context_member(..., extend_access_list=True)` uses a signed-in web session. CLI: `workspace member get-context-access/set-context-access` and `context add-member`.
- **Shared credential locking** (v0.45.0+): interoperates with TypeScript SDK 0.16.0+. Follow the README migration instructions before sharing credentials with another client; logout records revocation before deletion.
- **Workspace member management**: `WorkspaceClient` + `kagura workspace member|invite` — owner-key-only (server v0.42.0+, memory-cloud#1164). Assignable roles member|admin|viewer (owner → 422); member/viewer invites require `allowed_context_ids` (UUIDs, checked locally: the server failed on a non-UUID before v0.80.0 and answers 422 `VAL-001` since, memory-cloud#1693); `expires_in_days` presets 7/30/90/365; invitation ids are int with no status field; programmatic invite list nulls `token`/`invitation_url`; a user id of `.`, `..` or empty is refused (`_http.path_segment`; the CLI's `USER_ID`/`--user` exit 2) — percent-encoding leaves dot segments, so `remove_member(ws, "..")` would DELETE the workspace URL — and the `--workspace` UUID is checked before a confirm prompt (#285)
- **Owner-provisioned member keys**: `WorkspaceClient.mint_member_key/list_member_keys/revoke_member_key` + `kagura auth create-key/list-keys/revoke-key` (server v0.42.0+, memory-cloud#1165). Member/viewer targets only, never self; `expires_days` 1-3650 required; plaintext returned once (force-hidden after); revoke is soft
- **Agent bootstrap**: `KaguraClient.get_agent_bootstrap` (MCP) + `AgentsClient.bootstrap` (REST) — one-call session-start rehydration composing pinned + trusted recall + upcoming + state, fail-soft per component with top-level `degraded` (server v0.49.0+, RFC-0002 P0-3, memory-cloud#1276)
- **Agent registry + bindings** (#235, server v0.49.0+, memory-cloud#1274/#1275): registry `register/get/list/update/delete_agent` on both `KaguraClient` (MCP) and `AgentsClient` (REST); bindings are `bind_agent_context/list_agent_bindings/update_agent_binding/unbind_agent_context` on `KaguraClient`, mirrored as `bind_context/list_bindings/update_binding/unbind_context` on `AgentsClient`. Owner/admin-gated; `status` is the fail-closed kill switch, enforce→shadow is audited widening; bindings are subtractive (RBAC ∩ binding, `write_policy` deny|direct, max one `is_default`); `allowed_memory_types`/`allowed_source_types` reserved (#1286); metadata updates are set-only (null-clears not expressible)
- **Client-surface parity** (v0.38.0, #241-#244): `KaguraClient.recall_nearby(context_id, lat, lon, *, radius_m=1000, k=20)` — deterministic WHERE-axis query mirroring `recall_upcoming`, returns `distance_m`; radius_m/k are KEYWORD-ONLY. Write the location with `remember(details={"location": {"lat": <num>, "lon": <num>, "label": <str, optional>}})` — lat/lon must be JSON numbers (server v0.53.0+, memory-cloud#1331); `remember(supersedes=<uuid>)` shadows the old memory instead of destroying it like `forget`+`remember`, paired with `recall(include_superseded=True)` to read it back — a top-level arg, NOT a `filters` key (server v0.45.0+, memory-cloud#1208); `update_memory(details=...)` — **replaces details wholesale**, so round-trip `location` or it drops off `recall_nearby`; `list_tags(with_tags=[...])` server-side AND drill-down for faceted browsing (server v0.17.2+, memory-cloud#830). lat/lon must be JSON numbers — the server 422s string-typed coordinates by design; CLI `kagura update-memory --details/--location` (v0.42.0, #247) does the same and `--merge-details` does the reference() round-trip (top-level keys; it refuses a bounded reference reply whose details are omitted, memory-cloud 0.78.0+)
- **Forward-tolerant responses** (v0.38.1, #250): server-growing value sets on response models are plain `str` — `SleepReport.status`/`RollbackResult.status` (incl. `degraded`, server v0.43.0+, with `SleepReport.llm_call_failures`), `IndexerState.job_status`, `IndexerStateMetrics.skipped_reason` (incl. `memories_per_day_exceeded`, server v0.68.0+); the `SleepRunStatus`/`IndexerJobStatus`/`IndexerSkippedReason` Literals only document the known values. On MCP tool methods and the REST clients, a payload that still fails its model or envelope raises `KaguraResponseError` (`KaguraError` subclass, `.operation` = MCP tool name or `<Client>.<method>`), never a raw pydantic `ValidationError`/`KeyError` — parse new responses via `parse_response`/`parse_response_list` on `result.get(key)` (MCP) or `self._parse` + `self._expect_list(resp, op)` (REST). Every REST-backed `KaguraClient` method goes through `_rest_get(path, Model, params, operation="KaguraClient.<method>")` (`_rest_get_json` + `parse_response`; `list_memories` since #254, and since #277 `get_server_info`, `check_server_version` (reports `KaguraClient.get_server_info`), `get_embedding_status`, `get_memory_stats`, `find_duplicates`, `list_embedding_models`), so drift is `KaguraResponseError` there too, while a network failure, a non-JSON 2xx body and a non-2xx status other than 401/429 stay `KaguraConnectionError` (`_rest_get` applies `_rest_get_json`'s 404/422 → MCP-error remap only with `mcp_tool=`, as `_list_tags_via_rest` passes; the seven do not); `kagura doctor`'s `_check_server` turns that drift into a failed `server` check naming `/api/v1/system/info` (not "Server unreachable") and catches any other `KaguraError` (e.g. a 429) instead of letting it escape as a traceback
- **list_contexts / recall_upcoming options + supersede dismissal** (v0.39.0, #255): `list_contexts(*, name_contains, include_summary, include_details, include_stats)` — slim rows by default on server v0.73.0+ (`summary`/`embedding_model` opt-in, memory-cloud#1600); `count` is quota usage (ignores `name_contains`), `total` is rows returned, optional `hint` when nothing is visible (v0.75.0+, memory-cloud#1658); `recall_upcoming(include_details=True)` swaps each item's `trigger` for the full `details` (v0.73.0+, memory-cloud#1599); `update_memory(dismiss_supersede_candidate=True)` (KEYWORD-ONLY) rejects a supersede suggestion — `memory_id` only, `ValueError` with `external_id` (v0.65.0+, memory-cloud#1504; older servers drop it silently — only `supersede_candidate_dismissed` confirms). Each is sent only when set. CLI `kagura context list --name-contains/--summary/--details/--stats`, `kagura update-memory --dismiss-supersede-candidate`
- **Tool guardrails** (#253, server v0.74.0+, memory-cloud#1619/#1621): `load_guardrails(context_id, *, cap=None)` on `KaguraClient` (MCP) and `MemoryClient` (REST) → `GuardrailSet` (two independently capped lanes; per-lane `*_truncated` required; `format` > `GUARDRAIL_FORMAT` → treat as absent); `remember`/`update_memory(tool_trigger=ToolTrigger | dict)` → `details["tool_trigger"]` (both ways → `ValueError`; unknown keys are forwarded, so the server — the validator — refuses a typo; needs editor+ and a user credential); `ContextInfo.guardrails` block (absent with `?guardrails=off`, unparseable → `None`); `MemoryClient.get_guardrail_digest` → text + `tool_triggered_version` header; `forget` silently skips guardrails the caller may not delete

- **HTTPS check** (#274): `_http.validate_https_url` — run by every client (`KaguraClient`, the REST clients), `auth login --server`, `kagura-mcp`, `doctor` and setup — reads a URL as a parser does (`normalize_url`: trimmed, tabs/newlines/C0 controls dropped), scheme and loopback host case-insensitive (ASCII only), and any `http:` scheme (`http:/host`, `http:host` too) counts as plain HTTP; loopback HTTP is allowed in any case
- **Typed gate errors** (v0.39.0, #256, memory-cloud#1644): plan/quota refusals are typed by their `gate` descriptor (server v0.75.0+: MCP top-level envelope fields, REST `details`), falling back to the code on older servers — `gate="quota"`, or `quota_exceeded`/`QUOTA-001` naming a frozen `quota_type` or a retry window, or `QUOTA-002`/`CONNECTOR-001`, or MCP `rate_limit_exceeded` (in-band daily MCP call cap → `api_mcp_daily`, resets next UTC midnight) → `KaguraQuotaError` (`quota_type/limit/current/used_today/resets_at`, `retry_after` derived from `resets_at`; `None` for a count cap); `gate` plan|allowlist|deployment or `plan_required`/`feature_not_available`/`FEAT-001` → `KaguraFeatureNotAvailableError` (`feature/required_plan/required_plan_display/current_plan/gate`); both keep every server field in `.details`; an untyped `quota_exceeded`/`QUOTA-001` (the 1 MB guard; MCP answers `payload_too_large` from v0.108.0, REST keeps 429 `QUOTA-001`) stays plain `KaguraError`. - **Measurement lane + list bbox** (#254, server v0.54.0+, memory-cloud#1333/#1334): `KaguraClient.record_measurement(context_id, metric, value, *, measured_at, unit, details)` → `MeasurementResult` and `recall_series(context_id, metric, *, period, agg, start, end)` → `MeasurementSeries` of `SeriesBucket` — an append-only numeric HOW-MUCH lane with no delete, never embedded, never returned by `recall`, never merged or rewritten by Sleep consolidation (but an operator-set `SLEEP_MEASUREMENT_RETENTION_DAYS` > 0, server v0.55.0+, memory-cloud#1355, off by default, makes Sleep hard-delete old rows with no rollback). Metric 1-64 chars, finite non-bool value, unit 1-32 chars are checked locally; a naive `datetime` means UTC; server defaults day/avg/last 30 days, max 365-day window. `list_memories(*, lat_min, lat_max, lon_min, lon_max)` bbox — one-sided OK, `lon_min > lon_max` is the antimeridian box, any bound keeps only located memories, an out-of-range bound is a local `ValueError` — plus optional `MemoryListItem.location`. A drifted response from any of the three raises `KaguraResponseError`
- **Invite-only sign-up** (#259): `kagura auth login --invite <link|token>` — token checked locally against the server pattern (`^[A-Za-z0-9_-]{20,128}$`), never sent/stored/logged; `/join` link built from `verification_uri` (not `--server`), cross-server links refused before polling; raw `GET /api/v1/system/info` → `features.beta_invites` not `true` (off, or server < v0.70.0) drops the invite; server >= `device_flow.JOIN_RETURN_TO_MIN_SERVER_VERSION` (0.76.0, memory-cloud#1655/#1666) gets one `/join/<token>?return_to=<quoted /device?user_code=…>` link, older servers or a failed probe the two-step prompt (invite, then `/device`). A 429 from `device/authorize` (per-IP limit, server v0.76.0+, memory-cloud#1667) raises `KaguraAuthError` "Too many sign-in attempts…" with the `Retry-After` wait (default 60 s); `/oauth/token` polling is not rate-limited
- **Options the server ignored** (#273, TS kagura-memory-typescript-sdk#47): `list_tags(with_tags=[...])` goes to REST `GET /api/v1/contexts/{id}/tags` (one `with_tags` key per tag) on every server — MCP `list_tags` has `with_tags` only from v0.77.0 (memory-cloud#1669) and before that silently returned the unfiltered cloud; move it to MCP once `MIN_SERVER_VERSION` >= 0.77.0. Same `ListTagsResponse`; the route sends `context_name` from v0.77.0 (one request), and for an older server it comes from one `list_tags(limit=1)` MCP call per context, cached per client (a plain call fills it).
