# Kagura Memory SDK - Development Guide

## Overview

Python SDK for Kagura Memory Cloud. Seven clients:
- `KaguraClient` — MCP client for memory and context operations
- `ResourceClient` — REST client for resource token management and data ingestion
- `FilesClient` — REST + presigned PUT client for file uploads with sha256 integrity binding (server v0.15.1+)
- `SecretClient` — REST client for the zero-knowledge secret store (age recipient encryption, local decrypt; `[secret]` extra, server v0.39.0+)
- `WorkspaceClient` — REST client for workspace member/invitation management (owner API key only, OAuth rejected; server v0.42.0+)
- `AgentsClient` — REST client for the agent control plane: bootstrap (`POST /api/v1/agents/{agent_id}/bootstrap`) + registry/binding CRUD (owner/admin; server v0.49.0+)
- `MemoryClient` — REST client for tool guardrails: `load_guardrails` (`POST /api/v1/memory/guardrails`) + the `AGENTS.md` digest (`GET /api/v1/memory/guardrails/digest`) for API-key-only hooks and scripts (server v0.74.0+)

Checked against memory-cloud up to **v0.76.0** (production). `MIN_SERVER_VERSION` stays **0.17.1** and is advisory; newer surfaces carry their own server floor (README compatibility table).

## Key SDK Features

- Context management: `create_context`, `update_context` (with `resource_id`, `is_public`)
- Search tuning: `update_search_config` (semantic/bm25 weights, reranking). `recall(use_rerank=...)` is tri-state (server v0.69.0+, #251): `None` (default) omits the arg so the context's `search_config.use_rerank` applies (with `context_ids`, the first context's), `True` requests reranking (context must enable it), `False` is SENT to skip it; CLI `kagura recall --rerank/--no-rerank`
- **Server info + docs realign** (v0.39.0, #257): `get_server_info().features` types every v0.76.0 `/api/v1/system/info` flag (`neural_memory`, `research_tools`, `plan_page`, `byok`, `cost_display`, `managed_connectors`, `managed_llm`, `referrals`, `beta_invites`, `reranking`) as `bool = False` (`False` = not reported) with `extra="allow"` (newer flags → `features.model_extra`); `ServerInfo.search_defaults` = reranker defaults for new contexts (server v0.69.0+). Docstrings track the server: `load_pinned` → `memories` (never `results`); forget retention is per deployment (`CLEANUP_DELETED_MEMORIES_RETENTION_DAYS`, v0.66.0+) and `forget(query=...)` is refused while recall is `degraded`; recall `degraded`/`degraded_reason`, `tag_suggestions`, `filters.tags_normalize`, empty per-result keys omitted (v0.73.0+); `merge_contexts` counts rows + `pending_embedding`; public contexts/resources/tokens plan-gated (`plan_required`; since v0.68.0 by the `public_contexts`/`resources` plan feature, XL-only by default — earlier by the plan's shared contexts/token cap); reranker providers are `voyage|cohere|self_hosted` only (`self_hosted` v0.42.0+); `mcp_url` may carry `?profile=`/`?tools=` (v0.73.0+), which narrow `tools/list` only
- Resource ingestion: `setup_resource`, `ingest_event`, `ingest_events`
- Resource stats/schema: `get_resource_impact`, `get_resource_schema`
- **File uploads**: `FilesClient.upload/download_url/delete/list` with R2 sha256 binding (server v0.15.1+); optional `binding_context_id` binds a file to an owning context for ACL + nullable `FileObject.context_id` (server v0.41.0+). Against v0.41.0 the file-id endpoints require `workspace_id` on the query, so `download_url`/`delete` take a **required** `context_id` and the PUT sends the checksum header only when the presign signed it (#226)
- **Zero-knowledge secrets**: `SecretClient` + `kagura secret` — age recipient encryption, local decrypt; private key in OS keychain via `pyrage`/`keyring` (`[secret]` extra, server v0.39.0+). Owner-only hard delete via `SecretClient.delete_secret` / `kagura secret delete` (server v0.41.0+)
- **Workspace member management**: `WorkspaceClient` + `kagura workspace member|invite` — owner-key-only (server v0.42.0+, memory-cloud#1164). Assignable roles member|admin|viewer (owner → 422); member/viewer invites require `allowed_context_ids`; `expires_in_days` presets 7/30/90/365; invitation ids are int with no status field; programmatic invite list nulls `token`/`invitation_url`
- **Owner-provisioned member keys**: `WorkspaceClient.mint_member_key/list_member_keys/revoke_member_key` + `kagura auth create-key/list-keys/revoke-key` (server v0.42.0+, memory-cloud#1165). Member/viewer targets only, never self; `expires_days` 1-3650 required; plaintext returned once (force-hidden after); revoke is soft
- **Agent bootstrap**: `KaguraClient.get_agent_bootstrap` (MCP) + `AgentsClient.bootstrap` (REST) — one-call session-start rehydration composing pinned + trusted recall + upcoming + state, fail-soft per component with top-level `degraded` (server v0.49.0+, RFC-0002 P0-3, memory-cloud#1276)
- **Agent registry + bindings** (#235, server v0.49.0+, memory-cloud#1274/#1275): registry `register/get/list/update/delete_agent` on both `KaguraClient` (MCP) and `AgentsClient` (REST); bindings are `bind_agent_context/list_agent_bindings/update_agent_binding/unbind_agent_context` on `KaguraClient`, mirrored as `bind_context/list_bindings/update_binding/unbind_context` on `AgentsClient`. Owner/admin-gated; `status` is the fail-closed kill switch, enforce→shadow is audited widening; bindings are subtractive (RBAC ∩ binding, `write_policy` deny|direct, max one `is_default`); `allowed_memory_types`/`allowed_source_types` reserved (#1286); metadata updates are set-only (null-clears not expressible)
- **Client-surface parity** (v0.38.0, #241-#244): `KaguraClient.recall_nearby(context_id, lat, lon, *, radius_m=1000, k=20)` — deterministic WHERE-axis query mirroring `recall_upcoming`, returns `distance_m`; radius_m/k are KEYWORD-ONLY. Write the location with `remember(details={"location": {"lat": <num>, "lon": <num>, "label": <str, optional>}})` — lat/lon must be JSON numbers (server v0.53.0+, memory-cloud#1331); `remember(supersedes=<uuid>)` shadows the old memory instead of destroying it like `forget`+`remember`, paired with `recall(include_superseded=True)` to read it back — a top-level arg, NOT a `filters` key (server v0.45.0+, memory-cloud#1208); `update_memory(details=...)` — **replaces details wholesale**, so round-trip `location` or it drops off `recall_nearby`; `list_tags(with_tags=[...])` server-side AND drill-down for faceted browsing (server v0.17.2+, memory-cloud#830). lat/lon must be JSON numbers — the server 422s string-typed coordinates by design
- **Forward-tolerant responses** (v0.38.1, #250): server-growing value sets on response models are plain `str` — `SleepReport.status`/`RollbackResult.status` (incl. `degraded`, server v0.43.0+, with `SleepReport.llm_call_failures`), `IndexerState.job_status`, `IndexerStateMetrics.skipped_reason` (incl. `memories_per_day_exceeded`, server v0.68.0+); the `SleepRunStatus`/`IndexerJobStatus`/`IndexerSkippedReason` Literals only document the known values. On MCP tool methods and the REST clients, a payload that still fails its model or envelope raises `KaguraResponseError` (`KaguraError` subclass, `.operation` = MCP tool name or `<Client>.<method>`), never a raw pydantic `ValidationError`/`KeyError` — parse new responses via `parse_response`/`parse_response_list` on `result.get(key)` (MCP) or `self._parse` + `self._expect_list(resp, op)` (REST). `KaguraClient._rest_get` methods (`get_memory_stats`, `list_memories`, …) still raise `KaguraConnectionError` on drift
- **list_contexts / recall_upcoming options + supersede dismissal** (v0.39.0, #255): `list_contexts(*, name_contains, include_summary, include_details, include_stats)` — slim rows by default on server v0.73.0+ (`summary`/`embedding_model` opt-in, memory-cloud#1600); `count` is quota usage (ignores `name_contains`), `total` is rows returned, optional `hint` when nothing is visible (v0.75.0+, memory-cloud#1658); `recall_upcoming(include_details=True)` swaps each item's `trigger` for the full `details` (v0.73.0+, memory-cloud#1599); `update_memory(dismiss_supersede_candidate=True)` (KEYWORD-ONLY) rejects a supersede suggestion — `memory_id` only, `ValueError` with `external_id` (v0.65.0+, memory-cloud#1504; older servers drop it silently — only `supersede_candidate_dismissed` confirms). Each is sent only when set. CLI `kagura context list --name-contains/--summary/--details/--stats`, `kagura update-memory --dismiss-supersede-candidate`
- **Tool guardrails** (#253, server v0.74.0+, memory-cloud#1619/#1621): `load_guardrails(context_id, *, cap=None)` on `KaguraClient` (MCP) and `MemoryClient` (REST) → `GuardrailSet` (two independently capped lanes; per-lane `*_truncated` required; `format` > `GUARDRAIL_FORMAT` → treat as absent); `remember`/`update_memory(tool_trigger=ToolTrigger | dict)` → `details["tool_trigger"]` (both ways → `ValueError`; unknown keys are forwarded, so the server — the validator — refuses a typo; needs editor+ and a user credential); `ContextInfo.guardrails` block (absent with `?guardrails=off`, unparseable → `None`); `MemoryClient.get_guardrail_digest` → text + `tool_triggered_version` header; `forget` silently skips guardrails the caller may not delete
- **Claude Code setup** (#258): `kagura setup claude --scope project|user` — user goes through `claude mcp add-json --scope user` (`~/.claude.json` is only ever read); every scope is checked first (local > project > user, `-y` exits 1 when the new entry would be hidden) and `claude_code.find_kagura_mcp_entries` feeds `doctor`/`auth status` the effective entry + scope. `--guardrails off|<uuid>` (server v0.74.0+) / `--tool-profile NAME` (v0.73.0+) become `kagura-mcp --guardrails/--tool-profile`, which set `?guardrails=`/`?profile=` on the upstream URL at run time (`mcp_url_with_query`; never stored in credentials; `base_url_from_mcp` drops a query). `--[no-]session-hook/--[no-]sync-hook/--[no-]commands`; hooks are upserted and removed by exact SDK prefix, so a user's own `kagura …` hook survives. memory-cloud `kagura-memory` plugin detected via `claude plugin list --json` → interactive offer to skip the duplicate commands (default yes) and, separately, the SessionStart hook (default keep: the plugin has no automatic recall); never sets `guardrails=off`. API-key entry is `type: "http"` (legacy `url` still detected); at user scope it sends `Bearer ${KAGURA_MCP_API_KEY}` (`claude_code.MCP_API_KEY_ENV`, expanded by Claude Code at connect time) so the key never goes on `claude`'s argv, and `_add_user_entry` refuses any entry that `holds_credential`; the SessionStart hook runs `kagura recall --trusted-only`
- **Typed gate errors** (v0.39.0, #256, memory-cloud#1644): plan/quota refusals are typed by their `gate` descriptor (server v0.75.0+: MCP top-level envelope fields, REST `details`), falling back to the code on older servers — `gate="quota"`, or `quota_exceeded`/`QUOTA-001` naming a frozen `quota_type` or a retry window, or `QUOTA-002`/`CONNECTOR-001`, or MCP `rate_limit_exceeded` (in-band daily MCP call cap → `api_mcp_daily`, resets next UTC midnight) → `KaguraQuotaError` (`quota_type/limit/current/used_today/resets_at`, `retry_after` derived from `resets_at`; `None` for a count cap); `gate` plan|allowlist|deployment or `plan_required`/`feature_not_available`/`FEAT-001` → `KaguraFeatureNotAvailableError` (`feature/required_plan/required_plan_display/current_plan/gate`); both keep every server field in `.details`; an untyped `quota_exceeded`/`QUOTA-001` (1 MB guard) stays plain `KaguraError`. One rule in `_http.gate_error`, run by `_raise_for_mcp_error` and by `KaguraRestClient._gate_error` BEFORE the per-status hooks (so the 403 `QUOTA-001` token cap is no longer `KaguraConnectionError`, and `SecretClient`'s daily-quota 429 is `KaguraQuotaError`). `KaguraClient`'s HTTP-level 429 (incl. the middleware's daily MCP quota) stays `KaguraRateLimitError`. `partial_rollback` → `KaguraPartialRollbackError(.report_id, .summary)` (`summary=None` on drift, cause chained); `RollbackSummary` adds `merges_unreversible/importance_kept/promotions_kept` (`*_kept` = by-design skips); `FileIngestor` stops sending sections after the first `KaguraQuotaError`/`KaguraRateLimitError` (one error record per unsent section); CLI errors print `Resets at`/`Required plan`
- **Measurement lane + list bbox** (#254, server v0.54.0+, memory-cloud#1333/#1334): `KaguraClient.record_measurement(context_id, metric, value, *, measured_at, unit, details)` → `MeasurementResult` and `recall_series(context_id, metric, *, period, agg, start, end)` → `MeasurementSeries` of `SeriesBucket` — an append-only numeric HOW-MUCH lane, never embedded, never returned by `recall`, never touched by Sleep. Metric 1-64 chars, finite non-bool value, unit 1-32 chars are checked locally; a naive `datetime` means UTC; server defaults day/avg/last 30 days, max 365-day window. `list_memories(*, lat_min, lat_max, lon_min, lon_max)` bbox — one-sided OK, `lon_min > lon_max` is the antimeridian box, any bound keeps only located memories — plus optional `MemoryListItem.location`
- CLI: `kagura doctor`, `kagura auth login/refresh/status/list/create-key/list-keys/revoke-key`, `kagura setup claude [--scope user] [--guardrails off] [--tool-profile core] [--no-session-hook|--no-sync-hook|--no-commands]`, `kagura recall --trusted-only`, `kagura remember --details/--location`, `kagura ingest <file|url>`, `kagura resource setup/import/stats/schema`, `kagura files upload/list/delete/download-url`, `kagura secret keygen/put/get/grant/rotate/delete/exec`, `kagura workspace member list/add/set-role/remove`, `kagura workspace invite create/list/revoke`, `kagura context search-config`, `kagura sleep history/report/rollback`, `kagura guardrails load/digest [--out AGENTS.md]`, `kagura measure record/series`
