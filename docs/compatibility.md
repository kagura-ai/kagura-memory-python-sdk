# SDK ↔ memory-cloud Compatibility

Which memory-cloud server each release of the kagura-memory SDK needs, and the newest one it was checked against: one section per SDK release, newest first. Each surface newer than the SDK-wide floor carries its own floor in the section of the release that added it. A new release adds its section at the top, and the [README](../README.md#sdk--memory-cloud-compatibility) keeps a summary of the last five.

`MIN_SERVER_VERSION` in `src/kagura_memory/client.py` is **0.17.1**, the SDK's tested floor, and it is **advisory**: the SDK does not pre-check the server version and block a call. `check_server_version()` only logs a warning, and `kagura doctor` is the one place a too-old server fails outright. The two read the version the same way: a `v` prefix and `+build` metadata are ignored, a pre-release sorts below its release (`0.17.1-rc1` is below 0.17.1, `0.17.2-rc1` above it), and a version that does not start with `MAJOR.MINOR.PATCH` (`0.17`, `main-abc123`) is not compared, so no warning is logged and `kagura doctor` reports it as info. Version mismatches therefore surface **at call time**, in two different ways: a tool the server doesn't have raises `KaguraError` ("tool not found"), while a newer *parameter* on a tool it does have is typically ignored server-side — silently. That silent case is why the per-surface floors below matter. When pointing the SDK at a backend with `R2_CHECKSUM_BINDING_ENABLED=true`, the SDK must be v0.14.0+; older versions don't send the signed checksum header and uploads fail with `HTTP 403 SignatureDoesNotMatch`.

**Reading a section.** Its first paragraph, **Min memory-cloud**, is the floor: the memory-cloud release the SDK as a whole needs (`MIN_SERVER_VERSION`), the newest release that SDK release was checked against ("checked against memory-cloud up to …", in most sections from 0.39.0 on), and, under "Per-surface" or in parentheses, the newer release a method, CLI command or argument needs. A floor holds from that SDK release on, and a surface a newer section does not name keeps the floor an older section gave it. The rest of the section is that release's notes.

## 0.47.1

**Min memory-cloud:** 0.17.1 — checked against memory-cloud up to **0.161.0**. All per-surface floors remain as documented in the releases below; this patch changes local dependencies only.

**Python 3.11.5 or later ([#345](https://github.com/kagura-ai/kagura-memory-python-sdk/issues/345)).** The package now requires Python `>=3.11.5` (was `>=3.11`). Every Soup Sieve release that fixes GHSA-mmhr-3c5m-f64f, GHSA-6655-6qjp-jx7x and GHSA-7g44-g9rc-x53w (3.0.2, 4.0.0, 4.0.1) requires Python 3.11.5, so under the old floor the lock had to keep the affected Soup Sieve 2.10 for Python 3.11.0-3.11.4. The lock now selects Soup Sieve **4.0.1** only, and the `ingest-html` extra requires `soupsieve>=4.0.0`, so pip installs avoid the affected versions too. No other locked version changed. On Python 3.11.0-3.11.4, move to Python 3.11.5 or later before upgrading: pip there keeps resolving 0.47.0. Upgrade with `pip install --upgrade 'kagura-memory[ingest-html]'` (select the extras you use), or refresh your application's lock.

**How this was checked.** The release was checked against the memory-cloud source and schema at tag `v0.161.0` (the OpenAPI snapshot, the MCP tool schema fixture and the route, tool and service sources), compared with the same files at `v0.155.0`, plus mocked contract tests in this repository. **Upload malware scanning ([#337](https://github.com/kagura-ai/kagura-memory-python-sdk/issues/337), memory-cloud [#565](https://github.com/kagura-ai/memory-cloud/issues/565)).** A deployment can scan uploads for malware (off by default). Every file object carries `scan_status` from 0.160.0: `unscanned` (uploaded while scanning was off), `pending`, `clean`, `infected` or `error`. `FileObject.scan_status` is a plain `str`, so a value a newer server adds still parses, and `None` on an older server; `kagura files upload` / `kagura files list` print it. `FilesClient.download_url()` refuses a file the scan holds with `409`, now typed. `SCAN-001` (the scan has not finished, `Retry-After: 30`) raises `KaguraFileScanPendingError` with `retry_after` (the header's seconds, `None` when absent or not a number), `file_id` and `scan_status`. `SCAN-002` (blocked: `infected`, or with scanning on `error` or any value the server's allow-list does not pass) raises `KaguraFileBlockedError` with `file_id` and `scan_status`; waiting does not help, and an `infected` file stays refused after scanning is turned off. Both subclass `KaguraConnectionError`, which a 409 raised before, so existing handlers still catch them, and `code` / `details` stay the server's. The SDK does not retry: call again after `retry_after`. A file that downloaded before can answer `SCAN-001` again when the stored object no longer matches the scanned version (the server queues it for a new scan). The scan gate runs after the access checks, so an unreadable file is still `KaguraNotFoundError`, and the dedup `409 RES-002` of `upload()` is unchanged: it hands back a `pending` duplicate (which `download_url()` refuses for a while) but never a blocked one, whose 409 is raised with a message saying so. `kagura files download-url` says how long to wait, or that the scan blocked the file. With scanning on, an upload is also capped at the scanner's stream limit when that is lower than the per-file cap (both 100 MiB by default), refused as the usual validation error.

**Batch-level keys on items ([#338](https://github.com/kagura-ai/kagura-memory-python-sdk/issues/338), memory-cloud [#2753](https://github.com/kagura-ai/memory-cloud/issues/2753)).** From 0.156.0 a `remember_batch` item may carry `dedupe`, `tags_normalize` or `verbose` with the batch's own value. When the batch leaves one unset and every otherwise accepted item carrying it agrees on one valid value, that value applies to the whole batch and the reply's top-level `lint` gets a `batch_level_argument` entry (`{code, hint, subject}`), kept as `RememberBatchResult.lint`. An item whose value differs from the batch's is refused (`invalid_argument`); items that disagree with each other, or agree on an invalid value, are all refused, and with `atomic=True` any refused item refuses the whole batch. The server compares JSON type and value after `remember`'s string coercion (`"true"` equals `true`, `1` does not). The SDK no longer refuses such an item before the request; it sends the items as given and leaves the rule to the server. On older servers: 0.96.0-0.155.x refuse every item carrying one of the three keys (`invalid_argument` per item; a non-atomic batch writes the other items, an atomic one is refused whole), and 0.93.0-0.95.x ignore the item's key and write the item with the batch's setting, so an item-level `dedupe="check"` checks nothing there. A caller who needs one of them on such a server passes it on `remember_batch` itself.

**Service notices ([#339](https://github.com/kagura-ai/kagura-memory-python-sdk/issues/339), memory-cloud [#2762](https://github.com/kagura-ai/memory-cloud/issues/2762)).** From 0.161.0 a `bootstrap` reply may carry `notices` `{provenance, items: [{id, text, published_at, expires_at}]}`: service notices from the deployment's administrators, information to pass on to the user, not instructions. `BootstrapResponse.notices` types it as `ServiceNotices` of `ServiceNotice` (keys a newer server adds ignored), `None` when absent, and reads it fail-open: only `text` is required (an unreadable `id`, `published_at` or `expires_at` reads as `None`, so the notice is kept), a notice without readable text is dropped, and an unreadable block reads as `None` instead of failing the reply. Each notice is delivered once per person, and the server counts it delivered once it is placed in a reply, so show it when it comes; `kagura bootstrap` prints it with the rest of the reply. The server sends notices only when the deployment turned them on (`MCP_NOTICES_ENABLED`, off by default), to people who turned them on in their account settings, and only on a credential that speaks for that person (a session, an MCP OAuth token, or the person's own API key that is neither agent-bound nor a connector key), never on the google / microsoft views, the public endpoint or a share key; notices and `plan_headroom` share a quarter of `max_chars`, and a notice that does not fit waits for a call with more room. A headless connection can put `?notices=off` on its MCP URL so it does not use up notices nobody reads; the SDK keeps that query key as given. The per-user opt-in (`/api/v1/me/mcp-notices`, browser session only) and the admin notice routes are not wrapped.

**Google and Microsoft views ([#340](https://github.com/kagura-ai/kagura-memory-python-sdk/issues/340), memory-cloud [#2773](https://github.com/kagura-ai/memory-cloud/issues/2773), [#2778](https://github.com/kagura-ai/memory-cloud/issues/2778)).** From 0.158.0 `?profile=google` and its alias `?profile=microsoft` list the `core` tools without `describe_tools` and `guide`. `?add_tools=` cannot bring those two back, and a `tools/call` of either answers `unknown_tool` there, so `KaguraClient.describe_tools()` / `guide()` raise `KaguraError` with that code on such a URL. On these views `recall` makes no learning writes, and from 0.161.0 `bootstrap` carries no service notices. The server knows four profiles (`full`, `core`, `google`, `microsoft`, case-sensitive); the `--tool-profile` help of `kagura setup claude|codex|hermes|openclaw` and `kagura-mcp`, the `KaguraClient` `mcp_url` docstring and the README now say so, and the guardrail digest's `--profile` help lists all four. Setup still leaves the name to the server and refuses only a blank one or one starting with `-`.

**Passed through with no SDK change.** `details.event_phrase` resolves more phrases ([#2751](https://github.com/kagura-ai/memory-cloud/issues/2751)), and `details.event_direction` takes `"past"` or `"future"` ([#2752](https://github.com/kagura-ai/memory-cloud/issues/2752); the server refuses other values, and `update_memory(details=...)` drops the key unless it is sent again); the write lint code `event_date_mismatch` arrives in the dict replies and in a batch row's `lint`; `recall`'s optional `hint` (off by default on the server, MCP only) arrives in the dict reply (all 0.156.0). On `/api/v1/system/info` the new `features` flags (`connector_channel_routing` from 0.157.0; `email_signup`, `open_registration`, `provider_link_confirmation` and `system_admin` from 0.159.0) land in `ServerFeatures.model_extra`; the top-level `chatgpt_app_url` (0.157.0) and `announcement_consent_version` (0.159.0) are not typed.

**Auth.** The device flow, refresh and revoke the SDK uses are unchanged. The refresh-token exception for Google connected-apps clients, `client_secret_basic` at `/token` and the refusal to refresh a revoked row affect other OAuth clients only. A Google or GitHub sign-in finishes only in the browser that started it (0.160.0); the SDK never calls `/auth/{provider}/login` (`WorkspaceClient.from_web_session` takes a session cookie the user copies), so this does not apply.

**Not wrapped.** The optional OIDC provider, with `GET /api/v1/me/workspaces` and `GET /api/v1/me/workspaces/{workspace_id}/access` (OIDC access tokens only, 0.161.0); email sign-up, provider-link confirmation and announcement emails; `/api/v1/me/mcp-notices` and `/api/v1/memory-health`; the admin routes (memory health, operations status, service notices and the `SYSTEM_ADMIN_MODE` gate); connector channel routes and the worker config; `/.well-known/google-connected-apps`; and the MCP `get_file_download_url` / `list_files` tools. `MIN_SERVER_VERSION` stays **0.17.1**.

**Operation history ([#332](https://github.com/kagura-ai/kagura-memory-python-sdk/issues/332), memory-cloud [#2739](https://github.com/kagura-ai/memory-cloud/issues/2739)).** `WorkspaceClient.list_operation_history(workspace_id, *, query, context_id, actor, agent_id, operation, target_type, outcome, since, until, limit, cursor)` reads one page of `GET /api/v1/workspaces/{id}/operation-history` into `OperationHistoryPage` (`items`, `total`, `total_capped`, `next_cursor`, `retention_days`) of `OperationHistoryItem`. It needs a client built by `WorkspaceClient.from_web_session()`; one built with an API key or an OAuth token raises `ValueError` before any request, and the server takes no Bearer credential on this route. The caller must be an owner or admin of the workspace and the plan must include the `operation_history` feature; both are rechecked on every page, and a refusal is raised, never turned into an empty page: an expired session is `KaguraAuthError`, the plan gate `KaguraFeatureNotAvailableError` with `feature == "operation_history"`, and a refused filter (422) as well as the 403 `AUTH-101` "Insufficient permissions" `KaguraConnectionError`, which the server answers alike for a caller below admin, a non-member and an unknown or deleted workspace (on 0.154.0+ that route answers no 404; a 404, `KaguraNotFoundError`, means the server has no operation-history route, i.e. it is older than 0.154.0). The filters are checked before the request as the server checks them: `query` at most 120 characters, `actor` 255, `operation` 40 and `cursor` 512 (on the value as sent), `limit` 1-100, `context_id` / `agent_id` UUIDs, and `since` / `until` timezone-aware `datetime`s (a naive one is refused, not read as UTC) with `since` not after `until`; `since` / `until` are sent as the same instant in UTC (an offset with seconds would not parse on the server). Only a `None` filter is left out: every text filter must be a `str` and is sent as given, so a blank `query` / `actor` reaches the server as no filter and a blank `operation` is refused there (422), never widened into an unfiltered read; a blank `cursor` is a local `ValueError`, since the server never issues one and sending it would restart at page one. `target_type` and `outcome` are typed with the exported `OperationHistoryTargetType` / `OperationHistoryOutcome` Literals, and `operation` is a plain `str`, but none of them is checked against a value set locally, so a value a newer server adds needs no SDK release. The cursor is opaque and sent back as given; a paging loop should stop on any falsy `next_cursor`. The page's value sets (`principal_kind`, `surface`, `operation`, `target_type`, `outcome`) are plain `str`, and keys a newer server adds are ignored. `total` stops at 1,000 (`total_capped` is then true) while paging still reaches every match; `retention_days` is the workspace's window, 90 days plus its add-on. Recording starts when the server is deployed with the feature or the workspace moves to an entitled plan, with no backfill, and Free and Starter workspaces record nothing. A private context's events are visible to its creator only, a shared credential's owner is not asserted to be the person who made the call, and the history is not an immutable audit ledger and has no export. The server records the events itself: no SDK method writes history or retries a call for it. No CLI command or MCP method is added. The SDK consumes no plan feature list, so the new `operation_history` plan feature reaches it only as the gate's `feature`.

**Event-date order ([#333](https://github.com/kagura-ai/kagura-memory-python-sdk/issues/333), memory-cloud [#2724](https://github.com/kagura-ai/memory-cloud/issues/2724)).** `ListOrderBy` adds `event_start`, so `kagura list --order-by event_start` is accepted and `list_matching(order_by="event_start")` type-checks; memories without an event date sort last. A server before 0.152.0 refuses the value with its own error.

**Plugin `server_url` ([#334](https://github.com/kagura-ai/kagura-memory-python-sdk/issues/334), memory-cloud [#2690](https://github.com/kagura-ai/memory-cloud/issues/2690)).** The plugin's own setup keeps `context=<context-id>` in `server_url` when the MCP URL carries it and it is the context being configured, so its SessionStart hook names the default context. `kagura setup claude` now prints that `server_url`: it keeps `guardrails=off` and a `context=` whose first value is the same UUID as the printed `context_id`, and drops every other key (`guardrails=<id>`, `profile=`, `tools=`, `add_tools=`, another context). The MCP entry and the `--guardrails` / `--context` flags are unchanged.

**Sleep related index ([#335](https://github.com/kagura-ai/kagura-memory-python-sdk/issues/335), memory-cloud [#2728](https://github.com/kagura-ai/memory-cloud/issues/2728)).** `RollbackSummary.related_indexes_reverted` counts the `index_related` actions of the opt-in related index (`SLEEP_RELATED_INDEX_ENABLED`) that `rollback_sleep_run` undid, on `RollbackResult`, on `KaguraPartialRollbackError.summary` and in `kagura sleep rollback`'s output; it is 0 when the server sends no key, which it does unless at least one entry was reverted. `SleepAction`'s docstring lists `index_related`.

**Passed through with no SDK change.** `observed_weekday` (0.149.0) on rows and write replies; `event_start`, `event_end`, `event_weekday` and `event_unresolved` on rows and write replies, the `recall` / `list` filters `event_after` / `event_before` and `details.event_phrase` (0.152.0); `partially_unavailable_fields` on `reference(version=N)` (0.155.0). Rows and the `remember` / `update_memory` / `reference` replies stay dicts, `filters` and `details` are dicts, and a `RememberBatchItemResult` keeps a key it does not type in `model_extra`.

**Not wrapped.** Public MCP endpoint management, resource management grants, observation credentials and the observability API, and the `scope` / `context_id` filters of `GET /api/v1/files`. MFA and passkeys are browser-only. `MIN_SERVER_VERSION` stays **0.17.1**.
